Pavilion The problem

Twenty more guests shouldn't mean redrawing the room.

01

Plans are drawn, not checked

A drawing tool doesn't know what a wall, an aisle or an exit is. Nothing stops a row of chairs from blocking a door.

02

Every change is manual

A new headcount means moving rows by hand, recounting seats and repricing the hire list, then hoping the three still agree.

03

AI layouts are pictures

A generated layout that no code validated is a suggestion, not a plan. A venue crew can't build from it.

pavilion-nine.vercel.app02 / 12
Pavilion The principle

The engine decides.
The agent proposes. You apply.

Layout engine

Checks every write

Deterministic TypeScript. Objects stay inside the walls, never overlap, keep exits clear and respect locks. Seats and cost are computed, never guessed.

Agent

Works through the same actions

It can add, move and lock like you can. A redesign runs the planner and comes back as a proposal tied to a plan version. The plan itself doesn't change.

You

Hold the only Apply button

Compare before and after on the plan or in 3D, then apply or discard. The agent has no tool to apply a proposal or restore a version.

Pavilion Guardrails

Wrong moves are refused.
Nothing is saved.

The same check runs for a drag, an inspector edit and an agent call. The message names the objects that clash.

A proposal from an older version

Every write carries the version it was based on. Newer human work always wins; the proposal is regenerated, never merged.

Honest limits
Prices are example data, not supplier quotes.
Capacity is modelled seating, not legal occupancy.
The layout check is not a certified evacuation model.
The planner recommends layouts for theatre and banquet seating only.
